# Фаза 2: ведущий спит, команда работает

Ведущий просыпается, когда тик нашёл дело, делает ровно его и снова засыпает. Код не читает,
тестов не гоняет, вердиктов не ждёт, письма не пересказывает. Его дела: копии `QUEUED`, статусы
PLAN.md, состав state.md, лента, новые кодеры, ротация, эскалации, тихие участники, фаза 3.

`{plugin}` — строка `Plugin root:` из state.md, `<RUN DIR>` — абсолютный путь каталога
прогона. На событиях задач в ленте — счётчик `{done}/{total}`.

## Сон и пробуждение

Ведущий засыпает одним фоновым вызовом и заканчивает ход:

```
Bash(run_in_background=true):
  bash {plugin}/scripts/supervisor-wait.sh <RUN DIR> --root <корень репозитория>
```

Каталог прогона — только абсолютным путём: с относительным цикл не находит файлов (12–13.10.2026).
Подробно о цикле — `supervisor.md`, «Ход ведущего с супервизором».

Будит ведущего возврат цикла (в выводе уже лежат действия тика), сообщение участника или
уведомление о конце субагента. Если разбудил не цикл — сначала один разовый тик:

```
python3 {plugin}/scripts/supervisor-tick.py <RUN DIR>
```

Тик покажет всё, что накопилось, а не одно письмо, которое разбудило. Действия
разбираются сверху вниз, от P0 к P4. После каждого обработанного пробуждения цикл
запускается снова, и ход кончается. Ждать «пару минут и посмотреть» нельзя: ждёт скрипт.

Письмо, на которое ведущий ответил, закрывается `ack`. Аргументы строго в таком порядке, и
последним идёт имя файла письма (тик хранит только basename):

```
python3 {plugin}/scripts/supervisor-tick.py ack <RUN DIR> <имя файла письма>
```

Письмо DONE закрывается статусом DONE в PLAN.md, а при REOPENED — ещё и `ack` (раздел «Приёмка DONE»).

На пробуждении с P0 — сверка живых с `ListAgents`: смерть Claude-участника тик не видит, у него
нет процесса и маркера (23.09.2026 лимит API снял четырёх кодеров, тик показал лишь молчание).

**ENGINE_DOWN.** `TaskStop` прокси, затем по `fallback` (по умолчанию `claude`): обычный
Claude-участник под тем же именем — рецензент и техлид с промптом шага 5 (`phase1-planning.md`,
«Шаг 5: спавн команды») и `READY`, кодер с той же задачей. После `READY` замены — ей строки
`OPEN` из pending.log, а ждущим её —
`ROSTER UPDATE: <роль> заменён — если ещё ждёшь ответа, пошли запрос заново <роль>`.
`fallback: "fail"` — остановить прогон и доложить.

Особый случай: рецензент ушёл на Claude, а у `second-reviewer` движок тоже `claude`. Тогда
второе мнение выключается до конца прогона, новый рецензент не получает строку
`SECOND REVIEWER AVAILABLE:`, в ленту — одна строка ⚙️. Если движки разные, строка остаётся.
У `second-reviewer-{id}` замены нет: `TaskStop` и `status=stopped`, рецензенту `SECOND REVIEWER: none` и
второй строкой `task #<id>`, строку из `## Second opinions` убрать, `ROSTER UPDATE` не слать —
кодеры этого имени не знают.

## Приёмка DONE

`DONE:` кодера — заявка, а не факт. Задача становится DONE, только когда одноразовый
проверяющий, видевший одну задачу и её дифф, подтвердил каждый её критерий из PLAN.md.

Роль `acceptance-checker` всегда идёт на Claude: тип `supertick:spec-verifier`, фоном. Запись
о ней в конфиге игнорируется с одной строкой пользователю: внешний движок в режиме чтения не
запустит тесты задачи и даст ложный FAIL (так было в 121-374 с Cursor `--mode ask`).

Порядок:
1. В PLAN.md — `ACCEPTING(coder-N)`.
2. Одна команда пишет дифф коммитов из строки `COMMITS: <sha …>` письма DONE по файлам задачи;
   ведущий его не читает. Нет строки — взять SHA, названный в тексте DONE («Commit f2f8804»);
   нет и его — спросить кодера, по `git log` не угадывать (22.10.2026 вопрос был лишним кругом):

   ```
   git show <sha…> -- <файлы задачи> > <RUN DIR>/engine/accept-task<id>.diff
   ```

3. Спавн проверяющего. Первая строка промпта — слово режима:
   `ACCEPTANCE of task #<id>, team feature-<имя>.`, затем шапка `PLUGIN:` / `RUN DIR:` /
   `NAME:`, раздел задачи дословно между `--- TASK ---` и `--- END TASK ---`, строки
   `DIFF FILE:` (с SHA, дифф не пересобирать), `APPROVED DEVIATIONS:` (записи DECISIONS.md о
   задаче или её файлах, иначе `none`), `DEVIATION JOURNAL:` (путь
   `reports/deviations-*-task<id>.md`, если прокси его вёл), `OUT OF SCOPE:` из контракта.
4. Что проверяющий обязан сделать: по каждому критерию запустить команду или посмотреть
   файл и процитировать вывод; поставить PASS, FAIL или UNCLEAR; критерий, выполненный по
   одобренному отклонению, — PASS; отклонение из журнала, которого нет среди одобренных, —
   FAIL по задетому критерию. Плюс три общие проверки: дифф трогает только файлы задачи;
   тестовая команда задачи из Tooling зелёная (это единственное, что он запускает, и она
   ничего не меняет); за пределами объёма ничего не изменилось. Красный прогон тестов
   перезапустить до вердикта: пока другие кодеры гоняют тесты в том же дереве, одиночный
   красный ничего не доказывает (21.10.2026).
5. Ответ субагента ведущий одной записью кладёт в `reports/accept-task<id>.md` и читает
   только первую непустую строку. Она одна из двух:

   ```
   ACCEPT: task #<id> — PASS
   ACCEPT: task #<id> — FAIL
   ```

   Строка `ACCEPT:` в отчёте ровно одна и стоит первой: тик смотрит только первую непустую строку
   (PASS — `ACCEPT:` в её начале и слово PASS). Хотя бы один FAIL или UNCLEAR даёт FAIL.

Тик увидит файл и поднимет `accept_result`. **PASS** — DONE в PLAN.md; ждал шаг фазы 3 —
вернуться к нему; иначе новые кодеры; все кодовые DONE — фаза VERIFICATION. **Первый FAIL** (🔨),
до спавна свежего кодера, иначе тик сработает на старом FAIL и на старом DONE:
1. `mv <RUN DIR>/reports/accept-task<id>.md <RUN DIR>/reports/accept-task<id>-attempt1.md`;
2. `ack` старому письму DONE: `supervisor-tick.py ack <RUN DIR> <имя файла письма DONE>`;
3. `REOPENED(coder-M)` и свежий кодер с невыполненными критериями, путём `-attempt1.md` и handover.

**Второй FAIL** — задача как есть уходит в ручные проверки с обоими отчётами (⏸️). Отчёты
приёмки — и учёт: фаза 3 сверяет их число с задачами (17.09.2026 задача прошла трёх рецензентов
и тесты, потеряв уведомление для людей; поймал это только читатель общего диффа).

## Тихий участник и мёртвый прокси

Таймеров модели нет: 40 плановых пробуждений в одном прогоне не нашли ничего. Пока крутится
цикл, ручная проверка простоя (`team-runtime.md`, «Проверка простоя») не нужна — её делают
`deliver_pending`, `silent_too_long` и `first_minute_silent`. Остановленному или заменённому
участнику ведущий сразу ставит `stopped` (его единственная запись в `runs/`), иначе тик будит
ведущего по старой карточке каждые 20 секунд:

```
python3 {plugin}/scripts/run-state.py set <RUN DIR> <имя> status=stopped
```

**Claude-участник замолчал.** По неизменным файлам о смерти не судить. Сначала строки `OPEN`
в pending.log (может, он ждёт непереданное), потом `STATUS?` — он будит и уснувшего на своей
фоновой задаче (24.09.2026 сорок пять минут тишины кончились одним сообщением), потом
`ListAgents` (22.09.2026 рецензент «работал» 11 минут после смерти процесса). Заменять —
после второго неотвеченного `STATUS?`, и никогда поверх живого писателя: `TaskStop`, убедиться,
`status=stopped`, потом новый под новым именем. Два кодера на одних файлах губят несохранённое.

**Участник на движке.** Живость судится по маркерам, а не по имени процесса (раньше проверка
искала `codex|grok|kimi` и принимала живой `cursor-agent` за мёртвый). Одна команда, не
чаще раза в 15 минут и не больше трёх раз:

```
grep '"role": *"<имя>"' <RUN DIR>/ledger.jsonl | tail -3; {plugin}/scripts/run-engine.sh --status <RUN DIR> <имя>
```

| Последнее в ledger | `--status` | Значит |
|---|---|---|
| `launch` | `RUNNING` | работает, ждать: потолок держит `--timeout` |
| `launch` | `DEAD` | мёртвый прокси |
| `done` или `checks_done` 15+ минут назад | `DONE-UNREAD` | мёртвый прокси |
| `failed` | `DONE-UNREAD` со `status=failed` | как `ENGINE_DOWN` |
| `committed`, DONE не приходил | `taken` | работа сделана, потеряно сообщение: как DONE |

По часам не угадать (от двух минут до часа с лишним): `RUNNING` — ждать; `DONE-UNREAD` или
`DEAD` — попросить прокси доложить, дважды не ответил — замена. `pgrep -f` / `pkill -f` из
той же оболочки находят сами себя — не использовать. Маркеры — `engines.md`, «Запуск через run-engine.sh».

**Мёртвый прокси.** Ведущий не читает и не коммитит его работу сам. `TaskStop` и
`status=stopped`, затем свежий кодер под новым именем с брифом добивки: путь отчёта движка,
разрешённые файлы, проверить `git status`, пройти самопроверки, чинить возобновлением сессии
движка, закоммитить; реализацию не переделывать. В PLAN.md — `IN_PROGRESS(<новое имя>)`, в
ленту ⏸️. Добивщик стартует примерно с 90k контекста, ведущий с диффом — с 380k.

## Второе мнение

Выключено, пока в конфиге нет `second-reviewer`. Движок для него решается один раз на шаге
0b (`engines.md`, «Шаг 0b: разрешение движков») и посреди прогона не пересматривается — кроме
особого случая `ENGINE_DOWN` рецензента выше.

**Пришло `SENSITIVE: task #<id> — <почему>. Files: <список>.`** Рецензент стоит и ждёт, поэтому
ответ — в этом же ходу, раньше всего остального.
- В `## Engines` у `second-reviewer` есть движок: ответ `SECOND REVIEWER: <engine>` и второй
  строкой `task #<id>`. Движка нет или раздела нет: `SECOND REVIEWER: none` и `task #<id>`.
- При движке ведущий до спавна пишет дифф в `engine/second-reviewer-{id}-1.diff` (команды —
  `engines.md`, «Дифф в файле»): перенаправляет вывод, сам не читает; файлы из `<почему>` и
  `Files:` не открывает.
- Спавн `second-reviewer-{id}`: внешний движок — прокси, `claude` — `supertick:unified-reviewer`
  с контрактом второго мнения первым блоком (`engines.md`, «Второе мнение без файла агента»).
  В бриф идут задача, изменённые файлы из `Files:`, диапазон `git diff <Base Commit> -- <файлы>`,
  путь файла диффа. Ничего, что написал первый рецензент.
- В том же шаге строка `- second-reviewer-{id}: task #<id>, spawned HH:MM` в `## Second opinions`
  state.md.
- Повторный `SENSITIVE` по той же задаче получает тот же ответ; спавн — только если задачи ещё
  нет в `## Second opinions`.
- Ответ ушёл `queued` — строка в pending.log. Уведомление о конце хода рецензента со строкой
  `PARKED: task #<id> — waiting for SECOND REVIEWER` или с голым `SENSITIVE:` — это то же событие:
  ответить снова.

Строка `## Second opinions` уходит только при DONE задачи или при отмене экземпляра, а не
когда экземпляр закончил: отдавший находки и тихо умерший снаружи выглядят одинаково.

**Мнение не пришло.** Сюда приводят три пути: `ENGINE_DOWN` экземпляра (его прокси держит
`--timeout 1800`), проверка простоя, ротация рецензента. Сначала маркер:

```
{plugin}/scripts/run-engine.sh --status <RUN DIR> second-reviewer-{id}; ls <RUN DIR>/reports/review-task{id}-second-r1*.md
```

- `RUNNING` — не отменять, ждать `.done` фоном.
- `DONE-UNREAD` со `status=done` и файлом находок — переслать рецензенту
  `SECOND OPINION: task #<id>` со строкой `Findings: <путь>` и пометкой «переслал ведущий из ответа
  движка, прокси не разбирал»; находки не читать; `touch <out>.taken`, `TaskStop`,
  `status=stopped`, убрать строку. 23.09.2026 готовый отзыв Grok так пролежал почти час.
- `DEAD`, `failed`, `taken`, вызовов нет, экземпляр на `claude` — отмена: `TaskStop
  second-reviewer-{id}`, `status=stopped`, убрать строку, рецензенту `SECOND REVIEWER: none` и `task #<id>`.

Второго захода нет: экземпляр не пересоздаётся, движок не перезапускается, правило «мёртвый
прокси» не действует. Строка 🔬 в ленте закрывается один раз: успех — дайджестом ✅; провал —
строкой «второе мнение недоступно (причина), рецензент дальше один», если задача не DONE, такой
строки ещё не было и файла `reports/review-task{id}-second-r*.md` нет. Ветку без 🔬 (`none`,
тот же движок) закрывать нечем.

## Ротация рецензента

Каждые 3 завершённые задачи, не по таймеру: рецензенты однажды съели 55% бюджета, в другом
прогоне один дошёл до ~600k к четвёртой задаче; преемник стартует примерно со 100k. Счётчик
задач с последней ротации — в `## Team Roster` state.md.

1. `ROTATION` рецензенту: дописать текущее ревью, записать
   `reports/standing-unified-reviewer-{n}.md` не длиннее 15 строк (что повторяется, что уже
   решено, на что смотреть в оставшихся задачах; без пересказа отдельных ревью), прислать DONE
   со строками `UNANSWERED: coder-N task #M`.
2. Ждать DONE. Ротация ушла `queued` — повторять её на каждом уведомлении.
3. Если в `## Second opinions` что-то идёт, ротацию лучше отложить; если откладывать нельзя —
   до спавна преемника отменить все экземпляры целиком (раздел «Второе мнение», отмена).
4. Новый рецензент под тем же именем: промпт шага 5, `SECOND REVIEWER AVAILABLE:` по тому же
   правилу, блок `--- STANDING NOTES ---` со всеми записками предшественников. Ждать `READY`.
5. `ROSTER UPDATE` всем из `UNANSWERED` и кодерам с задачей `IN_REVIEW`; строки `OPEN` рецензенту —
   преемнику. `SendMessage` по имени отказал после респавна — писать по ref из ошибки или `ListAgents`.
6. Строка 🔄 в ленту.

`second-reviewer-{id}` не ротируется.

## Первая минута и контрольные точки

Часы участника идут от `startedAt` — его собственного первого `run-state.py set … status=running`.
Пока его нет, от `spawnedAt` карточки. Роль без задачи (рецензент, техлид) рождается `idle` и
первой минуты не имеет. Каждая тревога первой минуты звучит один раз.

- 60 секунд без признаков жизни — P2, ничего не делать.
- 3 минуты без `startedAt`, писем, правок файлов задачи и движка — P1: `STATUS?`. Не получил
  задачу (потерялся промпт, не то имя) — уточнить и перезапустить. Перезапуск — только после
  `TaskStop` прежнего.
- Дальше обычный надзор: контрольная точка каждые `checkAfterSec` (900, для задачи с риском или
  `Sensitive:` — 300). Два интервала без событий и без правок в файлах задачи — P0
  `silent_too_long`, и тоже сначала `STATUS?`.
- Если участник честно гоняет pytest, jest или сборку под `--root`, тик понизит тревогу до P3
  `busy`. Зависший процесс, начатый до окна молчания, не спасает — останется P0.

## Новые кодеры

На каждом PASS:
1. DONE в PLAN.md; доступна задача, которая TODO и чьи блокеры все DONE.
2. Пока активных кодеров меньше `--coders`: `IN_PROGRESS(coder-N)`, карточка
   `run-state.py new` прямо перед спавном, свежий кодер с промптом шага 5 (состав из state.md,
   раздел задачи дословно, handover блокеров, образцы, супервизор). Чужие правки в дереве —
   новый `git status --short` и блок `--- FOREIGN CHANGES ---` заново. Кодер на движке — прокси
   под тем же именем (`engines.md`, «Механика B: прокси»). Запись в состав state.md.

Каждому кодеру и риск-тестеру — свой `tmp/<тема>/` в каталоге прогона (общий scratchpad
затирают). Общий файл закрепляется за одним кодером, другие ждут, ведущий будит по очереди.

## Если застряли

- **STUCK кодера.** Ответить из того, что уже известно; исследователь — только если нужен
  непрочитанный код, а не на каждый STUCK. Можно уточнить задачу, разбить её или отдать
  другому. Указание — файлом ANSWER до сообщения:
  `{plugin}/scripts/team-mail.sh <RUN DIR> coder-N lead ANSWER task <id> -- "<ответ>"`.
- **Техлид и кодер не сошлись (MEDIUM)** — решает ведущий, при нехватке знаний зовёт
  веб-исследователя; итог в DECISIONS.md.
- **Образец не подходит** — MEDIUM к техлиду; иначе ведущий, перечитав брифы архитекторов.
- **Спор о серьёзности риска** — решает техлид, запись в DECISIONS.md.
- **Красная сборка после всех задач** — точечные задачи доработки, по кодеру на каждую.
- **CRITICAL требует другой архитектуры** — перепланировать и снова к техлиду.
- **Повторяются нарушения конвенций** — не хватает образца, пункт в задачу конвенций.
- **Лимит API (429) уронил нескольких участников.** Ничего не перезапускать вслепую. Сначала
  `run-engine.sh --status` по всем ролям на движках (движок мог досчитать: `DONE-UNREAD`), потом
  `runs/*.json`, `engine/*/`, `git status`, и только потом замены. Доделывающий кодер получает
  оставленный в дереве черновик как вход.

## После compaction

1. Один тик: он восстановит, кто где, по карточкам и письмам.
2. state.md, PLAN.md, pending.log; все строки `OPEN` доставить. `## Phase:` скажет, чьи
   инструкции исполнять.
3. Корень плагина: `test -x <Plugin root>/scripts/supervisor-tick.py`.
4. `## Engines` — как записано: конфиг не перечитывать, CLI не проверять; нет раздела — всё
   на Claude.
5. Каждая строка `## Second opinions` считается истёкшей и сразу разбирается по разделу
   «Второе мнение», «Мнение не пришло»; экземпляр на `claude` без маркера — истёкший.
6. Любая другая роль на движке — `--status` до перезапуска: `DONE-UNREAD` значит, ответ уже
   оплачен, его надо прочитать.
7. Снова цикл супервизора и конец хода.

## Дайджест задачи и шум

Лента — для человека, который ловит ошибку на лету: только то, что меняет поведение,
безопасность, объём или план; без мелочей ревью и механики, без повторов.

Дайджест принятой задачи: `✅ {done}/{total} <задача>: что теперь работает` и число кругов
ревью; при нужде строка «ревью поймало» (только поведение и безопасность) и строка крайних
случаев. Чистая задача — одна строка; DONE без блока дайджеста — одна строка по названию.
